## 1. How to use this document

- Each target has a stable id (`LS-PERF-NN`). Work on **one id per commit**; reference the id in
  the commit message and update this document (move the item to a "Done" list, or annotate it).
- Every target has a *Verification* section. Prefer measuring before/after with the harness in
  [Appendix A](#appendix-a--benchmark-harness) on the same machine and the same config.
- The dev site is small (132 hosts / 1279 services). Per-row costs and complexity are the useful
  numbers at that size; absolute totals are not. To demonstrate the superlinear items, increase
  the dataset first (see [2.4](#24-making-the-dataset-bigger)).
- Anything that changes the **output bytes** of a column is a compatibility break for Thruk,
  NagVis, PNP4Nagios and friends. Optimizations must keep query results byte-identical.

## 2. Measurement method and environment

### 2.1 Environment

- Container `naemon-dev-box-devbox-1`, OMD site `dev`.
- Naemon binary: `/src/naemon-core/src/naemon/.libs/lt-naemon`
  (this is the `naemon-core` checkout; it can be swapped for a branch build).
- Livestatus module: `/src/naemon-livestatus/src/.libs/livestatus.so`, configured in
  `/omd/sites/dev/etc/naemon/naemon.d/livestatus.cfg` with
  `max_cached_messages`, `thread_stack_size`, `pnp_path=/omd/sites/dev/var/pnp4nagios/perfdata`
  and the socket `/omd/sites/dev/tmp/run/live`.
- Queries were issued with `unixcat /omd/sites/dev/tmp/run/live` for spot checks and with the
  Python client in [Appendix A](#appendix-a--benchmark-harness) for timings.

### 2.2 Why a custom client

`unixcat` opens a new connection per invocation. Livestatus spawns **one pthread per
connection** (`module.c:110-193`), so `unixcat` timings include thread creation, connection
setup and teardown. That is fine for "real per-request cost from a cold client", but it buries
the query cost. The harness therefore uses one connection with `KeepAlive: on` and
`ResponseHeader: fixed16`, sends each query repeatedly on that connection, and reports the mean
of the repeated requests. This measures query CPU only.

Constructing a request line (the harness appends these automatically):

```
GET <table>
[Filter: ...]
[Columns: ...]
[Sort: ...]
[OutputFormat: ...]
KeepAlive: on
ResponseHeader: fixed16
<blank line>
```

The fixed16 response is a 16-byte header `%03d %11zu\n` (`OutputBuffer.cc:94-100`); the harness
parses the length and reads exactly that many bytes.

### 2.3 A note on caching

`LogCache` keeps up to `g_max_cached_messages` (default 500000, `module.c:71`) parsed log
messages in memory. The **first** `GET log` / `GET statehist` after a restart pays for reading
and parsing the log files; subsequent ones reuse the cache. Log/statehist numbers in this
document are for the warm case unless stated otherwise. This is why log timings have a "first"
and a "mean" column.

### 2.4 Making the dataset bigger

The dev site config is generated by `/omd/sites/dev/recreate.pl`
(`Monitoring::Generator::TestConfig`). To scale:

```
# edit hostcount / services_per_host in /omd/sites/dev/recreate.pl, then
perl /omd/sites/dev/recreate.pl
omd reload dev          # or restart naemon
```

`recreate.pl` currently uses `hostcount=100` (which produced 132 hosts) and
`services_per_host=10`. The machine is documented to handle ~10000 hosts. For scaling work,
`hostcount=5000` with 10 services is a good representative load; the quadratic targets
(`LS-PERF-01`, `LS-PERF-03`) will show up as a steep curve between 1000 and 5000 hosts.

### 2.5 Caveats

- Timings are from a shared container; treat differences under ~15% as noise. Prefer minimal
  times and paired before/after runs on the same box.
- The per-column ranking below used 20 iterations; the query-shape benchmark used 40–100.
- The `pnpgraph_present` cost depends on the filesystem backing `pnp_path`; on a network
  filesystem it is much worse than measured here.

## 3. Architecture summary

### 3.1 Threading

- The module registers its listening socket with naemon's iobroker
  (`module.c` `register_callbacks`/`open_socket`).
- `accept_connection()` (`module.c:110-165`) is called from naemon's main event loop. It calls
  `accept(2)`, `pthread_create()` for a **new thread per connection**, and appends the
  `pthread_t` to a growing `g_client_threads` array (`realloc` per accept).
- `client_thread()` (`module.c:167-193`) loops on `store_answer_request()` while the client asks
  for keep-alive. So one thread serves one connection and all requests on it.
- `reap_client_threads()` (`module.c:85-108`) is called on every accept and uses
  `pthread_tryjoin_np()` plus another `realloc` to shrink the array.
- `num_client_threads` is a **deprecated, ignored** option: `module.c:695-697` logs
  "there is no longer a limit to the number of concurrent threads". The dev config still passes
  `num_client_threads=20`, which has no effect.

### 3.2 Locking / shared state

- `LogCache` is protected by `_lock` (`LogCache.cc:58-72`) and is only locked for tables that
  report `hasLogcache()` (`TableLog`, `TableStateHistory`) — see `Store.cc:172-189`.
- `TableDownComm` (comments/downtimes) is protected by a recursive mutex
  (`TableDownComm.cc:21-45`, `lock()`/`unlock()` at `:258-278`).
- **Everything else is unprotected.** Query threads read `host_list`, `service_list`,
  `contact_list`, `command_list`, `timeperiod_list`, and the fields of live `host`/`service`
  objects while naemon's main thread mutates them. This is a pre-existing condition (the
  `origin/dev/thread_safety_downcomm` branch is related); it matters here because any new shared
  cache must be designed with it in mind.

### 3.3 Query pipeline

1. `Store::answerRequest` (`Store.cc:99-130`) reads the request, then
   `Store::answerGetRequest` (`Store.cc:158-211`) builds a `Query`.
2. `Query::Query` (`Query.cc:35-160`) parses the headers line by line. Each `Filter:` becomes a
   `Filter` object; each `Columns:` entry becomes a `Column*`; `Sort:`/`Stats:`/... are parsed.
3. `Query::start()` (`Query.cc:817-899`) runs wait conditions, prepends natural sort columns,
   allocates stats aggregators, and emits the header.
4. `Table::answerQuery()` (per table) iterates rows and calls `Query::processDataset()`.
5. `Query::processDataset()` (`Query.cc:913-998`) per row: response-size check, termination
   check, `_filter.accepts(data)`, authorization, time-limit check, then either `doStats()`
   aggregation or sorting or `printRow()`.
6. `Query::printRow()` (`Query.cc:1000-1012`) calls the virtual `Column::output(data, query)`
   of every requested column.
7. `Query::finish()` (`Query.cc:1014-1120`) emits grouped stats / sorted rows and the trailer.

### 3.4 NEB update path

`module.c` registers callbacks (comments, downtimes, program status, log, checks, ...). Comments
and downtimes are copied into `TableDownComm` objects (`TableDownComm::addComment`/`addDowntime`,
`:119-139`); log messages are parsed by `LogEntry` when a log query asks for them
(`Logfile::loadRange` → `processLogLine` → `new LogEntry` → `LogCache::handleNewMessage`). There
is **no** per-object materialization of host/service state; queries read the live naemon
structures.

## 3.5 How LMD uses this module

LMD is a Go daemon that merges several Livestatus backends (Naemon, Icinga, ...) into one
Livestatus endpoint. It uses the module in two distinct ways, and they have very different
performance profiles:

1. **Pull-sync its own copy of the data** from every backend in background goroutines. This is
   what the measurements below cover, and — at the configuration used — it is barely affected by
   LS-PERF-03/04.
2. **Proxy client queries.** When a client (Thruk, NagVis, ...) sends `GET ...` to LMD, LMD asks
   the backends for the same query and merges the rows. Those *are* the Thruk-style queries this
   document was written for: `AuthUser:`, `Sort:`, `Stats:`, `GET log`, `GET statehist`, joined
   columns such as `services_with_info`. LS-PERF-03/04 apply fully there. The sync loop is the
   exception, not the rule.

### 3.5.1 Sync configuration measured

From `/src/omd_utils/.gitignored/lmd_connected_to_omd_dev/lmd_connected_to_omd_dev.ini`:

| Option | Value | Meaning |
|---|---|---|
| `UpdateInterval` | 7 | delta pull every 7 s |
| `UpdateOffset` | 3 | pull window shifted back by 3 s |
| `FullUpdateInterval` | unset | no periodic full re-pull; delta only after the initial sync |
| `MaxParallelPeerConnections` | 1 | one backend connection at a time |
| `BackendKeepAlive` | true | one long-lived livestatus client thread |
| `IdleTimeout` / `IdleInterval` | 120 / 1800 | slower interval when idle |
| `[[Connections]] auth` | `""` | **no `AuthUser:` header on sync queries** |

`UpdateOffset` is why the logged filter values trail "now" by a few seconds:
`Filter: last_update >= 1790275176.665651` while the current time was ~1790275180.

### 3.5.3 Delta sync (every 7 s)

`hosts` and `services` are fetched with a `last_update >= t` filter and a reduced column set
(61 and 54 columns). Example, verbatim from the log:

```
GET hosts
OutputFormat: json
Columns: name ... num_services ... worst_service_state worst_service_hard_state ... last_update
Filter: last_update >= 1790275176.665651
```

`status`, `comments` and `downtimes` are re-fetched **in full, with no filter, on every loop**
(free on the dev site because it has 0 comments/downtimes). `hostgroups` and `servicegroups`
(with all their aggregate columns) are also re-fetched periodically.

Observed rows and fetch times over a ~2.5 minute run (`delta table:` log lines):

| Table | Rows per pull | Fetch time |
|---|---|---|
| `hosts` | 6–12 | ~0 ms (outliers 3 ms, 10 ms) |
| `services` | 266–276 | 1–2 ms (outliers 21 ms, 46 ms) |
| `comments` | all (0 here) | ~0 ms |
| `downtimes` | all (0 here) | ~0 ms |
| `status` | 1 | ~0 ms |

A steady-state sync therefore costs roughly **1–3 ms of livestatus query CPU every 7 s**
(~0.02–0.04 % of one core) on this configuration, dominated by the services delta.

Two facts drive the applicability ratings:

- the sync queries contain **no `AuthUser:`** (0 occurrences in the log), so the per-service
  authorization work that made LS-PERF-04 valuable is not paid;
- they contain **no `services_with_info` / `host_services_with_info`** (0 occurrences), so
  LS-PERF-03 never triggers.

## 5. Tier 1 — superlinear or syscall-bound

### LS-PERF-01 — `DownCommColumn` scans all comments/downtimes for every row, under one mutex

**Where**

- `src/DownCommColumn.cc:12-75` (`output`), `:95-115` (`isEmpty`), `:83-93` (`isNagiosMember`).
- `src/TableDownComm.cc:198-221` (`answerQuery`), `:229-256` (`findEntry`),
  `src/TableDownComm.h:25-43` (`_entries`, iterator accessors, `lock`/`unlock`).
- Consumed by `ListColumnFilter::accepts` (`src/ListColumnFilter.cc:20-42`).

**What it does**

`TableDownComm::_entries` is a single `map<unsigned long, DowntimeOrComment *>` holding every
comment/downtime. `DownCommColumn::output()` locks that map and iterates **all** entries for
**every row**, comparing `dt->_service == data || (dt->_service == 0 && dt->_host == data)`.
`isEmpty()` does the same scan under the lock. For filters, `ListColumnFilter::accepts` either
does `findEntry(id)` (a locked `map::find` per id) or `isEmpty()` (a full locked scan).

**Why it is slow**

- Complexity per row is O(total comments + total downtimes). For `GET services` with the
  `comments`/`downtimes` columns this is O(services × entries).
- The global mutex is held for the whole scan, so concurrent query threads serialise on it. The
  mutex is *recursive* (`TableDownComm.cc:33`), i.e. deliberately re-entrant, which makes the
  locking cheap to get wrong but not cheap to execute.
- Thruk asks for `comments`/`downtimes`/`comments_with_info`/`downtimes_with_info` on host and
  service lists. In an installation with tens of thousands of active downtimes during a
  maintenance window, this is quadratic.

**Measured**

The dev site currently has **0 comments and 0 downtimes**, so the scan is over an empty map and
costs ~0.15 ms extra on 1279 services. This target was therefore established from the code, not
from a scaling measurement. To measure it, create N downtimes (external commands
`SCHEDULE_HOST_DOWNTIME` / `SCHEDULE_SVC_DOWNTIME`) and plot `GET services Columns: downtimes`
against N; expect a straight line with slope O(rows).

**Fix**

Maintain a secondary index in `TableDownComm` keyed by the owning object:

- add `map<const void *, vector<unsigned long>>` (or two maps, host and service, or an
  `unordered_multimap`), updated in `add()` (`:142-167`) and `remove()` (`:169-196`).
- `output()` then iterates only the ids for the current object; `isEmpty()` is an

### LS-PERF-02 — `pnpgraph_present` performs an `access(2)` per row

**Where**

- `src/pnp4nagios.cc:21-51` — builds a path with `strcpy`/`strcat` and calls `access(path, R_OK)`.
- `src/HostSpecialIntColumn.cc:24` (`HSIC_PNP_GRAPH_PRESENT` → `pnpgraph_present(hst->name, 0)`).
- `src/ServiceSpecialIntColumn.cc:17` (`pnpgraph_present(svc->host_ptr->name, svc->description)`).
- Registered in `TableHosts.cc:305-306` (`pnpgraph_present`) and `TableServices.cc:337`.

**What it does**

For every row that requests `pnpgraph_present`, it constructs the PNP XML path and does a
filesystem `access()` to decide 0/1.

**Why it is slow**

- One syscall per row. On local disk this is ~1.4 µs; on NFS/CIFS it can be milliseconds and is
  a well-known cause of slow "add to graph" columns.
- Worse: `host_pnpgraph_present` on the **services** table calls `pnpgraph_present(host, 0)`
  once per service of the host, so it repeats the same host lookup S times.
- `pnpgraph_present` is commonly requested by Thruk alongside other columns, and there are two
  variants (host and service) in the same answer.

**Measured (dev site, 1279 service rows)**

| Column | mean | bytes | µs/row |
|---|---|---|---|
| `pnpgraph_present` (service) | 1.753 ms | 2558 | 1.37 |
| `host_pnpgraph_present` | 1.947 ms | 2558 | 1.52 |

This is the most expensive scalar column measured; the output is ~2 bytes/row.

**Fix**

- Minimum: a per-query memo keyed by `(host, service)` — for `host_pnpgraph_present` on the
  services table this collapses S calls to 1 per host. A natural home is `Query` state
  (`Query::table_tmp_storage` is already used by tables for per-query data, `Query.h:83`);
  introduce a proper per-query cache map instead of overloading that pointer.
- Better: a per-object cache with a TTL, invalidated on NEB events that change the graph file
  (a "graph created" event does not exist today, so TTL is simpler). Must be thread-safe.
- Alternative/complementary: do not offer the column unless `pnp_path` is set (it already
  returns -1 otherwise) and document its cost.

**Compatibility / risks**

- The return value is tri-state in `pnpgraph_present` (`-1` when `pnp_path` is unset, else 0/1),
  but the column is `int`. Preserve exact values.
- Caching introduces staleness: a graph that appears immediately after a check would be reported
  as absent until the TTL expires. Choose a short TTL (e.g. 30–60 s) and document it.

**Verification**

- Compare `GET services Columns: pnpgraph_present host_pnpgraph_present` output byte-for-byte

- Timing: the two columns above should drop by roughly the number of services per host.

**Effort:** small–medium.

### LS-PERF-03 — `*_services_with_info` / `*_services_with_state` re-walk the host's services for every row

**Where**

- `src/ServicelistColumn.cc:37-85` (`output`), registered in `TableHosts.cc:316-321` and on
  services as `host_services*` via the `_indirect_offset` join (`TableServices.cc:391-392`).
- `src/ServicelistStateColumn.cc:30-78` for the aggregate variants.

**What it does**

`ServicelistColumn::output` walks `servicesmember *mem` (the host's service list) and emits every
service (name; optionally state/has_been_checked; optionally plugin output). On the **services**
table the same column is reached through the `host_*` prefix, so it is executed once per service
row of the host.

**Why it is slow**

- O(S) per row; executed for each of the host's S service rows → O(S²) per host per query.
- It also re-renders the same text S times, so the answer size is inflated by the same factor.

**Measured (dev site)**

| Column | mean | bytes | µs/row |
|---|---|---|---|
| `host_services_with_info` | 2.687 ms | 1 051 877 | 2.10 |
| `host_services_with_state` | 1.739 ms | 235 792 | 1.36 |
| `host_services` | 0.349 ms | 176 652 | 0.27 |
| `services_with_info` (hosts table, 132 rows) | 0.254 ms | 90 110 | 1.93 |

The `host_services_with_info` answer is 1 MB for 1279 services — roughly a third of the full
`GET services` answer (3.29 MB) comes from this one column.

**Fix**

- Compute the per-host rendering once per query and reuse it for every row of that host. A
  per-query cache keyed by the host pointer, holding the rendered bytes (or a preformatted
  buffer), is the straightforward approach.
- A smaller variant: cache only the list of child strings and let the column still drive output;
  this avoids re-walking and re-formatting, at the cost of an extra copy. Measure both.

**Compatibility / risks**

- Output must stay byte-identical, including separators and the JSON list/sublist structure.
  Cache the *rendered* form per output format, or cache the child values and re-emit through the
  existing `Query` calls (safer).
- Authorization filters each child through `g_table_services->isAuthorized` — the cache key must
  include the auth user (or be per-query, which it naturally is).

**Verification**

- Byte-compare `GET services Columns: host_services_with_info` before/after.
- Timing should drop by roughly the average number of services per host.

**Effort:** medium.

**Implementation (commit 40b5140)**

`ServicelistColumn::output` was split into a cache wrapper and a `render()` helper. When the
column is joined (`_indirect_offset >= 0`, i.e. it reaches its object through a pointer stored in
the row, which is exactly when the same object repeats) `output()` looks the rendered bytes up in
a per-`Query` cache keyed by `(Column *, object)`. On a miss it redirects `Query`'s output to a
scratch `OutputBuffer`, calls `render()`, stores the bytes and emits them. Plain tables (each row
is a different object) render directly as before, so the hosts-table `services_with_info` case
does not pay for a cache it would never hit. The cache is bounded to 32 MiB.

Result (dev site, 132 hosts / 1283 services, keep-alive):

| Query | before | after |
|---|---|---|
| `host_services_with_info` | 2.75 ms | 1.04 ms |
| `host_services_with_state` | 1.75 ms | 0.30 ms |
| full `GET services` | 23.80 ms | 20.40 ms |

Correctness: for all 1283 service rows the cached `host_services_*` value is identical to the
uncached `*_services_*` rendering on the hosts table (3 variants, 0 mismatches).

### LS-PERF-06 — Missing single-object index for `Filter: name = X` (hosts, contacts, commands, groups)

**Where**

- `src/TableHosts.cc:362-392` (`answerQuery`) only consults `findIndexFilter("groups")`.
- `src/TableServices.cc:118-131` already does the equivalent for `host_name`, and `:133-150` for
  `groups`/`host_groups` — use it as the template.
- `src/StringColumnFilter.cc:104-110` (`indexFilter`) already returns the value for `OP_EQUAL`.
- `src/TableContacts.cc` (`answerQuery`), `TableCommands.cc`, `TableHostgroups.cc`,
  `TableServicegroups.cc`, `TableContactgroups.cc` have the same shape and `findObject()` methods
  that are currently only used by `WaitObject:` (`Query.cc:763-775`).

**What it does**

A `Filter: name = <host>` on the hosts table linearly scans `host_list` and evaluates the filter
on every host. There is no use of `find_host()` for this.

**Why it is slow**

O(n) per single-object lookup instead of O(1). Thruk repeatedly fetches one host/service by name

**Fix**

In `TableHosts::answerQuery` (non-`_by_group` path), before the linear scan:

```cpp
    host *host = find_host(host_name);
    if (host)

    return;
}
```

so this is correct for the `name` column. For the `_by_group` variants
(`hostsbygroup`), the index must instead iterate the groups that contain the host (or fall back
to the scan). Apply the same pattern to `TableContacts` (`find_contact`),
`TableCommands`, and the group tables (`find_hostgroup`, `find_servicegroup`,
`find_contactgroup`).

**Compatibility / risks**

- `find_host()` matches by name only, so it is safe for `Filter: name =`, but *not* for a filter
  on `alias`/`address` (those columns have different names and will not be returned by
  `indexFilter`).
- `AndingFilter::findIndexFilter` only sees top-level direct subfilters; an `Or:`-wrapped name
  filter is not used as an index — that is the desired conservative behaviour.
- The returned value is the `StringColumnFilter::_ref_string` buffer; `find_host` consumes it
  immediately, so no lifetime issue.

**Verification**

- `GET hosts Filter: name = <host> Columns: name` returns exactly one row and the same row as
  the unfiltered query filtered client-side.
- With a large config, timing should be flat in the number of hosts.
- Add a regression test for "filter by name returns the same row as a full scan".

**Effort:** small.

### LS-PERF-11 — by-group tables allocate a node per member per query

**Where:** `src/TableHosts.cc:332-360` (`by_group_parameters`, `by_hostbygroup`, `by_one_group`),
`cleanupQuery` at `:394-404`; the service equivalents in `TableServices.cc`
(`servicebygroup`, `servicebyhostgroup`, `cleanupQuery` at `:435-457`).

**Why slow:** for `GET hostsbygroup` / `servicesbygroup` / `servicesbyhostgroup`, a
`new hostbygroup` / `new servicebygroup` is allocated per (group, member) pair and chained on a
list that is walked and `delete`d after the query. At scale this is one malloc/free per row per
group membership.

**Fix:** allocate from a per-query arena/pool (`vector` of nodes reserved from the group's member
count, or a bump allocator tied to `Query`), or avoid materializing a wrapper by storing the
joined pair differently. `g_tree_foreach` gives no index, so a simple pre-sized
`std::vector<hostbygroup>` that does not reallocate is the smallest change.

**Compatibility:** the wrapper layout is used by the `indirect_offset` joins
(`TableHosts.cc:49-53`, `TableServices.cc:178-189`); do not change field order.

**Verification:** byte-compare `GET hostsbygroup` / `GET servicesbygroup`; measure allocations
with `valgrind --tool=massif` or a malloc counter across a large config.

**Effort:** medium.

### LS-PERF-12 — `HostContactsColumn`/`ServiceContactsColumn` build and sort a `std::list` per row

**Where:** `src/HostContactsColumn.cc:19-49`, `src/ServiceContactsColumn.cc:19-49`.

**Why slow:** per row, both build a `std::list<contactsmember*>`, push direct contacts and all
contact-group members, then `sort()` and `unique()`. That is one node allocation per contact plus
O(k log k) comparisons per row, for a value that only depends on the object's contact set.

**Fix:** precompute the merged/sorted contact list once per object per query (per-query cache),
or merge the two sorted lists without list-node allocation. If naive caching is too invasive,
replace `std::list` with a `std::vector` + `std::sort` + `std::unique` to at least remove the
per-node allocation.

**Compatibility:** the emitted names and their order (sorted, unique) must not change.

**Verification:** byte-compare `contacts` columns for objects with overlapping direct and group
contacts; benchmark a contact-heavy `GET hosts`.

**Effort:** small–medium.

### LS-PERF-14 — Sorting has no precomputed keys

**Where:** `src/RowSortedSet.cc` (`insert`/`extract`/`compare`), `src/Column.cc:31-36`
(`Column::compare`), `src/StringColumn.cc:24-26` (strcmp of `getValue`), `IntColumn.cc:31-37`,
`TimeColumn.cc:31-37`, `DoubleColumn.cc:29-34`.

**Why slow:** the sorter is a bounded max-heap. Every sift comparison is a virtual call into
`Column::compare`, which is another virtual `getValue` (possibly an `_indirect_offset` deref)
plus `strcmp`/numeric compare. For `Sort:` queries with no `Limit`, the heap holds the whole
result set → O(n log n) expensive compares. With `Limit`, it holds limit+offset — much cheaper,
but still per-insert log(limit) compares.

**Measured:** `GET services Columns: host_name description state` = 0.148 ms; adding
`Sort: description asc` = 0.635 ms (~4.3×). `Sort` + `Limit: 100` = 0.312 ms.

**Fix:** Schwartzian transform: for each row, compute the sort keys once (one pass over the
requested sort columns), store `(keys, row)` in a vector, then `std::sort` with a comparator that
only reads the cached keys, then emit. For bounded limits, a `std::partial_sort` or a
key-aware heap. This removes most virtual calls and repeated `getValue`/`strcmp`.

**Compatibility / risks:** the sort must be stable in the same way as today for equal keys; the
current heap is not stable, so exact ordering of equal rows may already be unspecified. Verify
against representative queries and keep multi-column precedence (`RowSortedSet::compare` order).
Note the natural sort columns are prepended for stats and sorting (`Query.cc:824-828`).

**Verification:** for a set of queries (single/multi column, asc/desc, with/without limit),
compare sorted output with the old implementation (allowing equal-key reordering to be checked
explicitly); benchmark `Sort` vs unsorted.

**Effort:** medium.

### LS-PERF-15 — Grouped stats: `vector<string>` per row + `map<vector<string>>`

**Where:** `Query.h:78-80` (`_stats_group_spec_t`, `_stats_groups_t`),
`Query.cc:1417-1434` (`getStatsGroup`), `:1436-1445` (`computeStatsGroupSpec`),
`Query.cc:944-965` (per-row group lookup in `processDataset`).

**Why slow:** for every accepted row, `computeStatsGroupSpec` pushes one `std::string` per group
column (via `Column::valueAsString`, which itself does `snprintf` for numerics and constructs a
`std::string`), then `_stats_groups.find(groupspec)` compares the `vector<string>` lexicographically
against every existing group. That is allocation + string comparison per row per group.

**Measured:** `StatsGroupBy: host_name` over 1279 services = 0.368 ms; not dramatic at this
scale because there are few groups, but the per-row allocations are visible in a profile.

**Fix:** hash the group key (e.g. concatenate with a separator and hash, or an
`unordered_map` keyed by a packed representation), avoid constructing `std::string`s for numeric
group columns (use a formatting buffer), and reserve/reuse the key buffer across rows.

**Compatibility:** group output order currently follows the sort (`Query::finish` extracts from
the sorter), so switching the map type must not change ordering. The group *values* must be
byte-identical.

**Verification:** byte-compare grouped-stats output for string and numeric group columns; measure
`StatsGroupBy: custom_variables` / `host_name` at scale.

**Effort:** medium.

### LS-PERF-16 — Log path overheads

**Where**

- `src/LogEntry.cc:13-64` (constructor), `:468-488` (`updateReferences`), `:397-415`
  (`handleProgrammEntry`).
- `src/Logfile.cc:125-147` (`loadRange`), `:169-192` (`processLogLine`).
- `src/LogCache.cc:169-246` (`handleNewMessage`).
- `src/PerfdataAggregator.cc:16-43` (`consume`).
- `src/TableLog.cc:170-183` (`column`), joined columns registered at `:76-82`.

**Why slow / what to fix**

1. **Two `strdup`s per line**: `_msg` (destructively tokenized) and `_complete` (kept intact for
   the `message` column and for `_options`). A single allocation holding both copies (or one
   intact buffer + offset-based tokenization) halves the allocation count. The comment at
   `LogEntry.cc:25-26` already flags `_complete` as memory-hungry.
2. **Up to four hash lookups per line**: `updateReferences()` calls `find_host`, `find_service`,
   `find_contact`, `find_command`. If the query does not request the joined `current_*` columns
   (and no auth user needs them), these are wasted. The query's column set is known at
   `loadRange` time via the `Query*` passed from `TableLog::answerQueryReverse`; thread a flag
   through `logcache`/`load()` so references are only resolved when needed. This is a larger but
   high-value change for log-heavy installations.
3. **`strstr` classifier**: `handleProgrammEntry` (`:397-415`) runs four `strstr` calls on every
   line that the earlier handlers did not classify; the comment in the constructor calls it a
   "Performance killer". Replace with a prefix/length check (the strings are short and fixed) or
   a single pass.
4. **Joined-column blow-up**: `GET log` with no `Columns:` requests all ~450 columns, including
   all `current_host_*`, `current_service_*`, `current_contact_*`, `current_command_*`. For
   entries where `_host`/`_service` is NULL, every joined column is still invoked and emits an
   empty value. Measured: a 3-column 1-hour log query is 15.7 ms / 23.6k rows (0.66 µs/row) while
   the all-columns variant is 445.7 ms (18.9 µs/row) for 36.3 MB. A realistic Thruk query names
   its columns, but the all-columns form should not be ~30× more expensive per row than the data
   warrants. Options: skip output of a joined column group in bulk when the joined pointer is
   NULL (needs the column to know its group), or precompute the "null joined object" fast path.
5. **`PerfdataAggregator::consume`** (`:16-43`) `strdup`s the whole perfdata string per row
   before parsing (because `next_field` modifies it). Parse the existing string with a
   non-destructive scanner, or copy into a reusable per-aggregator buffer.

**Measured (dev site, 1-hour window, 23 624 rows, warm cache)**

| Query | mean | bytes |
|---|---|---|
| `log` 3 columns | 15.66 ms | 10 568 245 |
| `log` all columns | 445.74 ms | 36 300 600 |
| `log` all columns + sort | 450.81 ms | 36 300 600 |
| `log` stats | 0.80 ms | 6 |
| `statehist` 6 columns | 18.82 ms | 44 714 |
| `statehist` sorted | 19.20 ms | 44 714 |
| `statehist` stats | 18.79 ms | 2 |

**Compatibility / risks**

- `_msg`/`_complete` are used via pointers (`_text`, `_options`, `_host_name`, ...); keep the
  pointer semantics and null-termination.
- Lazy `updateReferences` must not break `TableLog::isAuthorized`, which uses `_host`/`_service`
  (`TableLog.cc:151-168`), nor the joined columns.
- State history (`TableStateHistory.cc`) is a separate, heavier algorithm (see LS-PERF-16a
  below) and depends on `LogEntry` fields.

**Verification**

- Byte-compare log answers (with and without joined columns) and statehist answers.
- Measure `GET log` with the realistic column set Thruk uses and the all-columns set.
- `valgrind --tool=massif` or a heap counter for memory.

**Effort:** medium–large (split into sub-commits).

#### LS-PERF-16a — State history algorithm (secondary)

`TableStateHistory::answerQuery` (`TableStateHistory.cc:161-521`) walks all log entries for the
timeframe and maintains a `map<HostServiceKey, HostServiceState*>`. Points worth profiling
separately:

- Host state changes iterate all of the host's services and call `updateHostServiceState` for
  each (`:433-443`); timeperiod transitions iterate the whole `_state_info` map (`:462-467`).
- When sorting is on, `process()` (`:720-765`) copy-constructs a full `HostServiceState` (which
  copies the `_services` vector, `HostServiceState.h:50`) and `strdup`s `_log_output` per emitted

- `updateHostServiceState` re-`strdup`s `entry->_options` for `TIMEPERIOD_TRANSITION` (`:671-699`)
  even though `answerQuery` already parsed it (`:446-469`).

Measure with an availability-report-shaped query (`Filter: time > ...`, `Sort: host_name`,
`Stats: duration`) before changing anything.

## 7. Tier 3 — architecture

### LS-PERF-17 — Unbounded thread-per-connection

**Where:** `src/module.c:85-193` (`reap_client_threads`, `accept_connection`, `client_thread`),
`:695-697` (deprecated `num_client_threads`), `:56-58` (`g_thread_stack_size`,
`g_client_threads`, `g_num_client_threads`).

**Issues**

- One `pthread_create` per accepted connection, no pool, no upper bound. A burst of short
  connections (many clients, or a client that does not keep-alive) creates and destroys a thread
  each time.
- Per accept: `pthread_tryjoin_np` over the whole array, a `realloc` to grow, and after
  completion another `realloc` to shrink. This is O(connections) work on the accept path, which
  runs in naemon's main event loop.
- Each thread gets a 64 KiB stack by default (`module.c:56`); with `max_cached_messages` and
  per-thread `InputBuffer`/`OutputBuffer` this multiplies memory.

**Fix**

- A bounded worker pool with a connection queue, or (simpler, keeps the existing thread body) a
  reusable thread that accepts "hand off this fd" work items and returns to the pool. Reaping
  becomes O(1) amortised.
- Reuse a `std::vector<pthread_t>` with reserve/doubling instead of `realloc` per accept.
- If keep-alive is used by all clients, consider capping concurrent connections and rejecting
  beyond the cap with a proper response code.

**Compatibility / risks:** the `g_should_terminate` cooperative shutdown
(`module.c:480-490`) and the `g_client_threads` join loop must be rethought for a pool. This is
the largest change in this document; do it after the smaller targets unless thread count is the
observed bottleneck.

**Verification:** connection-rate benchmark (many short unixcat connections) and a
`/proc/<pid>/status` thread-count/RSS comparison.

**Effort:** large.

### LS-PERF-18 — No cross-request caching / repeated work

**Where:** whole query path. `Store::answerGetRequest` (`Store.cc:158-211`) always builds a fresh
`Query`, scans the live lists, and renders.

**Observation:** Thruk polls the same shapes every few seconds (host list, service list, problem
counts). Every poll re-evaluates filters and re-renders output that changed little. There is no
per-table data generation counter, no ETag-like mechanism, and no result cache.

**Possible directions**

- A per-table monotonically increasing generation counter bumped from the NEB callbacks, plus a
  short-TTL memo of (normalised query → bytes). Invalidation is the hard part: any host/service
  field can change without a dedicated NEB event.
- Safer subset: cache only the expensive *derived* values that are pure functions of one object
  and a query constant (the per-host service aggregates of LS-PERF-03/04, the pnpgraph result of
  LS-PERF-02) inside a single query.
- A `Count`-style fast path for the very common "count hosts/services matching a filter" query.

**Recommendation:** do not start here. Land the per-query caches first; they are prerequisites and
deliver most of the benefit without cross-query invalidation risk.

**Effort:** large / design.

### LS-PERF-19 — Data races on host/service lists (prerequisite)

**Where:** query threads (`module.c:167-193`) read `host_list`, `service_list`, `contact_list`,
`command_list`, `timeperiod_list` and live object fields with no lock; naemon's main thread
mutates them from NEB callbacks and external commands.

**Why it matters for performance work:** any new shared cache (per-object aggregates, pnpgraph
results, contact lists) must be either per-query (no sharing, no race) or protected/published
correctly. The existing `origin/dev/thread_safety_downcomm` branch and the `TimeperiodsCache`
mutex are the current state of that discussion. Per-query caches (LS-PERF-02/03/04/12) avoid the
problem entirely and should be preferred as the first step.

**Effort:** background/architectural.

## 8. Cross-cutting notes

### 8.1 naemon-core compatibility facts checked

- `find_host(const char*)` is a pure `g_hash_table_lookup(host_hash_table, name)`
  (`naemon-core/src/naemon/objects_host.c`), so using it for `Filter: name =` is correct.
- `find_service(host_name, svc_desc)` is a hash lookup on the composite key
  (`objects_service.c`), already used by `TableServices` for the `host_name` index.
- `host` and `service` have `comments_list` (`objects_host.h:125`, `objects_service.h:116`) but
  **no** per-object downtime list, so LS-PERF-01 needs a livestatus-side index.
- naemon's `check_time_against_period()` gained a local-day cache in the recent performance work
  (`naemon-core` branches `perf-event-loop` / `perf-experiments`), but livestatus does not call it
  per row; it uses its own `TimeperiodsCache`. If livestatus ever moves to calling naemon's
  function, note the caveat that it now has a process-wide static cache and is not safe to call
  concurrently from query threads.
- `CURRENT_NEB_API_VERSION` was bumped in the naemon performance work (9, and 10 after the
  `object_ptr` hardening on the integration branch). Any NEB module — including `livestatus.so`
  — must be rebuilt against the matching headers or naemon refuses to load it. Remember this when
  testing a livestatus change against a naemon branch build.

### 8.2 Output correctness is a hard constraint

Thruk, NagVis, PNP4Nagios and others parse these answers. Every optimization that touches
formatting must be validated with byte-for-byte comparison, not just "the numbers look right".
The harness should grow a "golden output" mode (run a fixed query, hash the body) for the columns
a change touches.

### 8.3 Useful knobs

| Option | Where | Effect |
|---|---|---|
| `max_cached_messages` | `module.c` (`g_max_cached_messages`, default 500000) | log cache size; bigger means fewer re-parses, more RSS |
| `max_lines_per_logfile` | `module.c` (`g_max_lines_per_logfile`, default 1000000) | cap on lines read per logfile |
| `max_response_size` | `module.c` (`g_max_response_size`, default 500 MiB) | aborts a query when the buffer exceeds this |
| `thread_stack_size` | `module.c` (`g_thread_stack_size`, default 64 KiB) | per-connection thread stack |
| `pnp_path` | broker module args | enables `pnpgraph_present` (access() cost) |
| `g_disable_statehist_filtering` | `TableStateHistory.cc:27` | disables the object-filter pre-pass |

## Appendix A — benchmark harness

Save as `livestatus-bench.py` (Python 3, stdlib only). It speaks the livestatus protocol over a
unix socket with keep-alive so timings exclude connection/thread setup.

```python
#!/usr/bin/env python3
"""Tiny keep-alive benchmark client for naemon-livestatus.

Usage:
  livestatus-bench.py SOCKET queries
  livestatus-bench.py SOCKET rank-cols TABLE [PREFIX]
  livestatus-bench.py SOCKET log [NOW]

SOCKET is e.g. /omd/sites/dev/tmp/run/live.
"""
import socket, statistics, sys, time

class Conn:
    def __init__(self, path):
        self.s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
        self.s.settimeout(300)
        self.s.connect(path)

    def _read(self, n):
        b = b""
        while len(b) < n:
            d = self.s.recv(n - len(b))
            if not d:
                raise EOFError("connection closed")
            b += d
        return b

    def req(self, query):
        self.s.sendall((query + "KeepAlive: on\nResponseHeader: fixed16\n\n").encode())
        hdr = self._read(16)
        n = int(hdr[4:15])
        return self._read(n)

def bench(c, name, query, n=50):
    body = c.req(query)                       # warm-up / first run
    ts = []
    for _ in range(n):
        t0 = time.perf_counter()
        c.req(query)
        ts.append(time.perf_counter() - t0)
    print("%-46s %9.3f ms  min %9.3f ms  bytes %10d"
          % (name, 1000 * statistics.mean(ts), 1000 * min(ts), len(body)))

QUERIES = [
    ("hosts all",                    "GET hosts\n"),
    ("services all",                 "GET services\n"),
    ("scan only (services)",         "GET services\nColumns: host_name\n"),
    ("hosts svc-aggregates",         "GET hosts\nColumns: name num_services num_services_ok num_services_warn num_services_crit num_services_unknown num_services_pending num_services_hard_ok num_services_hard_warn num_services_hard_crit num_services_hard_unknown worst_service_state worst_service_hard_state\n"),
    ("hosts comments/downtimes",     "GET hosts\nColumns: name comments comments_with_info downtimes downtimes_with_info\n"),
    ("services comments/downtimes",  "GET services\nColumns: host_name description comments downtimes\n"),
    ("services contacts",            "GET services\nColumns: host_name description contacts contact_groups\n"),
    ("hosts timeperiods",            "GET hosts\nColumns: name in_check_period in_notification_period\n"),
    ("hosts pnpgraph",               "GET hosts\nColumns: name pnpgraph_present\n"),
    ("services pnpgraph",            "GET services\nColumns: host_name description pnpgraph_present host_pnpgraph_present\n"),
    ("services sort",                "GET services\nColumns: host_name description state\nSort: description asc\n"),
    ("services json",                "GET services\nOutputFormat: json\nColumns: host_name description state\n"),
    ("stats hosts",                  "GET hosts\nStats: state = 0\nStats: state = 1\nStats: state = 2\n"),
    ("stats grouped host",           "GET services\nStatsGroupBy: host_name\nStats: state = 0\nStats: state = 2\n"),
    ("columns table",                "GET columns\n"),
    ("status",                       "GET status\n"),
]

LOG_QUERIES = lambda now: [
    ("log 1h 3 cols",   "GET log\nFilter: time > %d\nFilter: time < %d\nColumns: time type options\n" % (now - 3600, now)),
    ("log 1h all cols", "GET log\nFilter: time > %d\nFilter: time < %d\n" % (now - 3600, now)),
    ("log 1h stats",    "GET log\nFilter: time > %d\nFilter: time < %d\nStats: state = 0\n" % (now - 3600, now)),
    ("statehist 1h",    "GET statehist\nFilter: time > %d\nFilter: time < %d\nColumns: host_name service_description time from until duration state\n" % (now - 3600, now)),
    ("statehist sorted","GET statehist\nFilter: time > %d\nFilter: time < %d\nSort: host_name asc\nSort: service_description asc\nColumns: host_name service_description time from until duration state\n" % (now - 3600, now)),
]

def rank_cols(c, table, prefix=""):
    raw = c.req("GET columns\nColumns: table name\n").decode()
    names = []
    for line in raw.splitlines():
        if not line:
            continue
        parts = line.split(";")
        if len(parts) >= 2 and parts[0] == table:
            names.append(parts[1])
    rows = []
    for nm in names:
        try:
            body = c.req("GET %s\nColumns: %s\n" % (table, nm))
            ts = []
            for _ in range(20):
                t0 = time.perf_counter()
                c.req("GET %s\nColumns: %s\n" % (table, nm))
                ts.append(time.perf_counter() - t0)
            rows.append((1000 * statistics.mean(ts), nm, len(body)))
        except Exception as e:
            print("ERR", nm, e, file=sys.stderr)
    rows.sort(reverse=True)
    print("%-38s %9s %10s %10s" % ("column", "ms", "bytes", "ms/row"))
    for ms, nm, b in rows[:30]:
        print("%-38s %9.3f %10d %10.4f" % (nm, ms, b, ms / max(1, len(body.splitlines()))))

def main():
    path = sys.argv[1]
    mode = sys.argv[2] if len(sys.argv) > 2 else "queries"
    c = Conn(path)
    if mode == "queries":
        for name, q in QUERIES:
            bench(c, name, q)
    elif mode == "log":
        now = int(sys.argv[3]) if len(sys.argv) > 3 else int(time.time())
        for name, q in LOG_QUERIES(now):
            bench(c, name, q, n=5)
    elif mode == "rank-cols":
        rank_cols(c, sys.argv[3], sys.argv[4] if len(sys.argv) > 4 else "")
    else:
        print(__doc__)
        sys.exit(2)

if __name__ == "__main__":
    main()
```

### Extracting LMD's column sets

LMD logs every backend query at `LogLevel = "Trace"`. This parses them into distinct
(table, extra headers, columns) shapes and is how section
[3.5](#35-how-lmd-uses-this-module) was produced:

```python
import re, collections
raw = open("/src/lmd/lmd_connected_to_omd_dev.log", "rb").read().decode("utf-8", "replace")
raw = re.sub(r"\x1b\[[0-9;]*m", "", raw)          # strip ANSI colour
shapes, cols = collections.Counter(), {}
for m in re.finditer(r"query: (GET [^\n]*)\n(.*?)(?:\n\n|\Z)", raw, re.S):
    head, rest = m.group(1).strip(), m.group(2)
    table = head.split()[1]
    filters = tuple(sorted(l for l in rest.splitlines()
                           if l.split(":")[0] in ("Filter", "Sort", "Limit")))
    c = next((l[9:] for l in rest.splitlines() if l.startswith("Columns: ")), "")
    shapes[(table,) + filters] += 1
    cols.setdefault((table,) + filters, c)
for k, n in shapes.most_common():
    print(k, "x", n)
    print("   ", cols[k])
```

To benchmark a shape, put its column list into a query in the harness above (add it to
`QUERIES` or call `bench()` directly), and pin the row count with `Limit:` to LMD's observed
delta/initial sizes (10 hosts, ~270 services) so the comparison is not dominated by how many
checks happened to finish. That is exactly how the table in
[3.5.5](#35-how-lmd-uses-this-module) was produced.
